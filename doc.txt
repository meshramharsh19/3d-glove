PROJECT OVERVIEW
================================================================================

3D-GLOVE is a Geospatial Urban Survey & Property Management Platform built with
modern web technologies. It provides a professional interface for visualizing and
managing urban infrastructure including:
  • 3D properties and houses with textured models
  • Utility poles (electric, light, communication, traffic signals, CCTV)
  • Sewage pipeline networks with geospatial data
  • Overlay layers (roads, custom KML maps)
  • Real-time property updates via WebSockets
  • Interactive tools (measurements, street view, PDF reporting)

The project consists of:
  - FRONTEND: Interactive 3D visualization web application
  - BACKEND: Express.js REST API + MongoDB database + WebSocket server

HOW THE PROJECT WORKS - ARCHITECTURE
================================================================================

1. FRONTEND - USER INTERFACE
   ├─ Browser loads index.html with Cesium + Three.js viewers
   ├─ JavaScript modules initialize in numbered order (1_config → 10_banner)
   ├─ Cesium creates a 3D map viewer with geospatial capabilities
   ├─ Three.js loads OBJ/MTL textured 3D property models
   ├─ Map layers (roads, houses, paths) are overlaid on base map
   └─ UI provides tools: search, measure, street view, PDF reports

2. BACKEND - SERVER & DATABASE
   ├─ Express.js server (port 4000) handles HTTP requests
   ├─ MongoDB stores all data (poles, pipelines, banners, etc.)
   ├─ Socket.IO enables real-time bidirectional communication
   ├─ Routes handle CRUD operations for:
   │  ├─ Poles (CREATE, READ, UPDATE, DELETE)
   │  ├─ Sewage Pipelines (CREATE, READ, UPDATE, DELETE)
   │  └─ Banners (Associated with properties)
   └─ WebSocket events broadcast updates to all connected clients

3. COMMUNICATION FLOW
   ├─ REST API calls: Frontend → Backend (HTTP)
   │  └─ Requests: POST /api/poles/add-pole, GET /api/poles, etc.
   ├─ Real-time Updates: Server → Frontend (WebSocket)
   │  └─ Events: pole_updated, pipeline_changed, etc.
   ├─ Geospatial Rendering: 3D data → Cesium/Three.js visualization
   └─ Coordinate Systems:
      ├─ Geodetic: Longitude, Latitude, Height (WGS84)
      └─ Cartesian: X, Y, Z (Legacy support)

4. DATA PERSISTENCE
   ├─ MongoDB Collections:
   │  ├─ poles            [Utility poles with geospatial data]
   │  ├─ sewagepipelines  [Pipeline networks with coordinates]
   │  └─ banners          [Annotations linked to properties]
   └─ Features:
      ├─ Automatic timestamps (createdAt, updatedAt)
      ├─ Indexed queries for fast lookups
      └─ Geospatial indexing for location-based queries

POLE MANAGEMENT ROUTES (/api/poles)
================================================================================

POST /api/poles/add-pole
  Description: Add a new utility pole to the database
  Request Body:
    {
      "poleNumber": "P001",              (string, required, unique identifier)
      "type": "electric",                (enum: electric, light, communication, 
                                          traffic_signal, cctv_surveillance)
      "voltage": "11kV",                 (string, optional)
      "poleHeight": 15.5,                (number, optional, in meters)
      "wireHeading": 180,                (number, optional, bearing in degrees)
      "installationDate": "2024-01-15",  (ISO date string, optional)
      "position": {
        "longitude": 79.1234,            (number, geodetic coordinates)
        "latitude": 28.4567,
        "height": 200                    (elevation in meters)
      },
      OR use legacy format:
      "x": 500, "y": 600, "z": 50        (cartesian coordinates, alternative)
    }
  Response:
    {
      "success": true,
      "pole": {
        "_id": "ObjectId",
        "poleNumber": "P001",
        "type": "electric",
        ...full pole document...
      }
    }
  Status: 201 Created | 400 Bad Request | 500 Server Error

GET /api/poles
  Description: Retrieve all poles with pagination and filtering
  Query Parameters:
    ?page=1&limit=50&type=electric&search=P001
  Response:
    {
      "success": true,
      "poles": [...array of poles...],
      "total": 150,
      "page": 1,
      "limit": 50
    }
  Status: 200 OK | 500 Server Error

GET /api/poles/:poleNumber
  Description: Retrieve a specific pole by its number
  Path Parameter: poleNumber = "P001"
  Response:
    {
      "success": true,
      "pole": {...pole document...}
    }
  Status: 200 OK | 404 Not Found

PUT /api/poles/:poleNumber
  Description: Update an existing pole's properties
  Request Body: (any fields to update)
    {
      "voltage": "22kV",
      "poleHeight": 16.5,
      "status": "active"
    }
  Response:
    {
      "success": true,
      "pole": {...updated pole document...}
    }
  Status: 200 OK | 404 Not Found | 400 Bad Request

DELETE /api/poles/:poleNumber
  Description: Remove a pole from the database
  Response:
    {
      "success": true,
      "message": "Pole deleted successfully"
    }
  Status: 200 OK | 404 Not Found

WEBSOCKET EVENTS (Real-time Communication)
================================================================================

Connected Client listens for:
  • pole_updated       - A pole's data has changed
  • pole_added         - New pole added
  • pole_deleted       - Pole removed
  • pipeline_updated   - Pipeline data changed
  • pipeline_added     - New pipeline added
  • banner_updated     - Property annotation changed

Client can emit:
  • request_pole_update     - Request latest pole data
  • request_pipeline_update - Request latest pipeline data
  • broadcast_location      - Share user's current location

POLE MODEL (MongoDB Collection: poles)
================================================================================
{
  _id: ObjectId,                    [Auto-generated MongoDB ID]
  poleNumber: String,               [Unique identifier, required]
  type: String,                     [electric, light, communication, etc]
  voltage: String,                  [e.g., "11kV", "22kV"]
  poleHeight: Number,               [Height in meters]
  wireHeading: Number,              [Bearing in degrees 0-360]
  installationDate: Date,           [ISO date of installation]
  
  position: {
    longitude: Number,              [WGS84 longitude]
    latitude: Number,               [WGS84 latitude]
    height: Number                  [Elevation above sea level]
  },
  
  x: Number,                        [Legacy cartesian X coordinate]
  y: Number,                        [Legacy cartesian Y coordinate]
  z: Number,                        [Legacy cartesian Z coordinate]
  
  createdAt: Date,                  [Auto-generated timestamp]
  updatedAt: Date                   [Auto-updated on modifications]
}

Pole Type Normalization:
  Input "Electric Pole" → Normalized to "electric"
  Input "concrete" → Normalized to "electric"
  Input "light_pole" → Normalized to "light"
  Input "CCTV" → Normalized to "cctv_surveillance"
  Input "traffic signal pole" → Normalized to "traffic_signal"

Supported Pole Types:
  • electric              [Standard electric transmission/distribution poles]
  • light                 [Street lighting poles]
  • communication         [Telecom, fiber optic poles]
  • traffic_signal        [Traffic management poles]
  • cctv_surveillance     [Security and monitoring poles]

  points: [                         [Array of coordinate points]

DEVELOPMENT SETUP & RUNNING PROJECT
================================================================================

PREREQUISITES:
  • Node.js (v14 or higher)
  • npm (Node Package Manager)
  • MongoDB Atlas account (or local MongoDB)
  • Internet connection for Cesium/Three.js CDN resources

INSTALLATION:

1. Install Backend Dependencies:
   $ cd backend
   $ npm install

2. Install Frontend Dependencies (if needed):
   $ cd frontend
   $ npm install

3. Configure Environment Variables:
   Create .env file in backend folder:
   MONGODB_URI=mongodb+srv://username:password@cluster.mongodb.net/survey?appName=Cojag
   PORT=4000
   NODE_ENV=development

4. Start Backend Server:
   $ cd backend
   $ npm start
   
   Server runs on: http://localhost:4000
   WebSocket connects to same address
   MongoDB connection attempts with retry logic

5. Start Frontend Development Server:
   Option A: Use Live Server VS Code extension (click "Go Live")
   Option B: Use python -m http.server 8000 (Python 3)
   Option C: Use npx http-server
   
   Frontend runs on: http://localhost:5500 (or chosen port)

6. Access Application:
   Open browser: http://localhost:5500 (or your frontend port)
   Application loads all 3D visualization and starts communicating with backend

IMPORTANT NOTES:
  • Frontend must know backend URL (check 1_config_globals.js)
  • Backend port is typically 4000, adjust if conflicts
  • MongoDB URI can be localhost or remote (MongoDB Atlas)
  • Cesium and Three.js load from CDN

Build and run entire stack:

KNOWN ISSUES & IMPORTANT CONSIDERATIONS
================================================================================

1. FRONTEND PORT & API CALLS
   • Frontend often runs on Live Server (port 5500+)
   • Frontend must explicitly target http://localhost:4000 for API calls
   • Relative paths like /api/poles may not work from different port
   • Solution: Use full URL with explicit backend port

2. COORDINATE SYSTEMS
   • Poles support both Geodetic (lat/lon/height) and Cartesian (x/y/z)
   • Geodetic is preferred (WGS84 standard)
   • Cartesian support is legacy; new data should use Geodetic
   • Conversions handled in conversion.js module

3. POLE TYPE NORMALIZATION
   • Pole types automatically normalized to standard values
   • Examples: "Electric Pole" → "electric", "concrete" → "electric"
   • Only 5 valid types: electric, light, communication, traffic_signal, cctv_surveillance
   • Validation happens on backend

4. SEWAGE PIPELINE VALIDATION
   • Minimum 2 points required for pipeline
   • All points must have valid latitude (-90 to 90), longitude (-180 to 180)
   • Height field optional, defaults to 0
   • Material and status enums are case-sensitive

5. MONGODB CONNECTION
   • Connection requires working internet and network access
   • MongoDB Atlas cluster must not be paused
   • User IP must be whitelisted in MongoDB Atlas
   • Connection string must include appName parameter
   • DNS resolution required for mongodb+srv:// URIs

6. REAL-TIME UPDATES
   • Socket.IO establishes persistent WebSocket connection
   • Disconnections auto-attempt reconnect
   • Events broadcast to all connected clients
   • Check browser console for connection status

TROUBLESHOOTING GUIDE
================================================================================

ISSUE: Backend server crashes on start
SOLUTION:
  1. Check MongoDB connection: Ensure cluster is running and not paused
  2. Verify .env file has correct MONGODB_URI
  3. Check DNS: Run 'nslookup 1.1.1.1' to verify DNS resolution
  4. Review error logs for specific MongoDB errors
  5. Try with local MongoDB first to isolate the issue

ISSUE: Frontend can't connect to backend
SOLUTION:
  1. Verify backend is running on port 4000: curl http://localhost:4000
  2. Check browser console for CORS errors
  3. Verify API calls use http://localhost:4000, not relative /api paths
  4. Check firewall/port forwarding if using remote backend
  5. Verify Socket.IO connection in browser Network tab

ISSUE: 3D models not loading
SOLUTION:
  1. Check browser console for loading errors
  2. Verify model files exist in frontend/files/ directory
  3. Check OBJLoader/MTLLoader scripts loaded correctly
  4. Verify file paths match exactly (case-sensitive)
  5. Check browser's CORS policy allows loading models

ISSUE: Real-time updates not working
SOLUTION:
  1. Check Socket.IO connection status in browser console
  2. Verify WebSocket works: Check Network tab for ws:// protocol
  3. Ensure server.js imports socket.js handlers
  4. Check event names match between emit and listen
  5. Restart both backend and frontend

ISSUE: Poles/Pipelines don't appear on map
SOLUTION:
  1. Verify data saved in MongoDB: Query directly via MongoDB Atlas
  2. Check pole_placement.js and sewagePipeline.js modules
  3. Verify Cesium viewer initialized properly
  4. Check coordinate values are within valid ranges
  5. Verify layer visibility is enabled in UI

ISSUE: PDF generation fails
SOLUTION:
  1. Verify jsPDF library loaded: Check Network tab
  2. Check browser console for jsPDF errors
  3. Ensure report data populated correctly
  4. Check PDF permissions and security settings
  5. Try different browser if issue persists

================================================================================
KEY TECHNICAL CONCEPTS
================================================================================

GEODETIC COORDINATES:
  • Based on WGS84 (World Geodetic System 1984)
  • Longitude: -180° to +180° (East-West)
  • Latitude: -90° to +90° (North-South)
  • Height/Altitude: Elevation above sea level (meters)
  • Used by GPS and modern geospatial applications
  • Preferred format for this project

CARTESIAN COORDINATES:
  • X, Y, Z coordinate system (Euclidean 3D space)
  • Legacy support for backward compatibility
  • X: typically East-West
  • Y: typically North-South
  • Z: elevation or depth
  • Conversion to geodetic via conversion.js

WEBSOCKET (Socket.IO):
  • Persistent bidirectional communication between client and server
  • Unlike HTTP (request-response), WebSocket maintains open connection
  • Enables real-time updates with minimal latency
  • Auto-reconnection on disconnect
  • Event-based messaging system
  • Scales to many concurrent connections

MONGODB & MONGOOSE:
  • NoSQL document database
  • Schema validation via Mongoose ODM
  • Collections: poles, sewagepipelines, banners
  • Automatic timestamps (createdAt, updatedAt)
  • Indexing for performance optimization
  • Geospatial queries possible

3D RENDERING:
  • Cesium.js: Geospatial globe with map tiles, GIS overlays
  • Three.js: WebGL 3D graphics, model rendering, custom geometry
  • Both run simultaneously in same application
  • Cesium for geographic context
  • Three.js for detailed 3D objects/buildings
  • Proper coordinate transformation between systems
